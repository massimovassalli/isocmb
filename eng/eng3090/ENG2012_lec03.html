Last week you read a program nobody had documented, described it to an assistant, and then did the thing that matters: you ran both versions on a list of cases and compared the answers.

That is not a one-off exercise. From today it is the normal way to work.

Important

SPECIFY — say exactly what the step must do. DIAGNOSE — check what came back, before you believe it.

Your job, and its job

This course will not make you fluent in Python syntax, and does not try to.

You are not going to be writing complex structured programs yourself — nested loops, branching logic, data structures. The machine does that, quickly and well.

What you must be able to do is orchestrate: decide the steps, know exactly what goes into each one and what comes out, and check that what came back is right.

Warning

Nobody will ask you to defend a loop. They will ask you to defend the number at the end — and “the AI wrote it” has never been an answer to “why is this patient’s heart rate 42?”

Three things, today

  1. Read a signature — what a step needs, and what it gives back
  2. Call it, and catch what comes back — and know where it went
  3. Check it — on an ordinary case, on the edges, and on data built so that you already know the answer

The thing that does all three is a function: a named box with an opening on each side.

Note

Inside the box is the machine’s territory. The edges of the box are yours.

A program is a sequence of calls

The data

Five minutes of a wearable recording, one reading every 15 seconds — the one you annotated last week.

readings = [78, 82, 0, 104, 110, 100, 96, 0, 300, 132]
interval_s = 15

Nothing has been shown to you yet. To see a value, you have to ask:

length = len(readings)
print(length)
10

Note

Two functions already. len computes a value, and we catch it in length. print shows it on the screen and gives nothing back.

Functions you already have

highest = max(readings)
lowest = min(readings)
print(highest)
print(lowest)
300
0

Always the same shape: a name, brackets, what goes in, and a value that comes out.

Calls can be nested. Python works from the inside out: first len(readings) becomes 10, then print is handed the 10.

print(len(readings))
10

Caution

lowest is 0 and highest is 300. Both are correct, and both are nonsense: one is a dropped sample, the other an artefact. The function did exactly its job. It is not its job to know what your numbers mean.

Where functions live: import

Python keeps most of its functions out of the way until you ask for them.

from statistics import mean, median

readings = [78, 82, 0, 104, 110, 100, 96, 0, 300, 132]

print(mean(readings))
print(round(mean(readings), 0))
print(median(readings))
100.2
100.0
98.0

statistics is a module: a file of functions that came with Python. The second line is three functions in one: mean hands its value to round, which hands its value to print.

Warning

The mean is 100.2 bpm — tachycardia, and a phone call to the ward. It is the average of seven real readings, two dropped samples and one artefact. The average of nonsense is nonsense.

mean did its job perfectly. Whether the answer means anything is a different question, and it has its own name in our framework: VALIDATE, in week 6.

Two ways to import

from statistics import mean, median      # bring two names in
average = mean(readings)
import statistics                        # bring the whole module in
average = statistics.mean(readings)

Same function, same result. In the first, mean becomes a name in your file. In the second it stays inside statistics, and you say where it came from every time you use it.

Note

The set of names a file knows is its namespace. The second form keeps the module’s names in their own namespace, which is why it is longer to type and tells the reader more. With your own modules, later today, that matters.

Tip

For the curious: with from statistics import mean, a later line of yours saying mean = 5 quietly replaces the function, and the next call fails with a baffling message. With import statistics, statistics.mean is still there. Short names are convenient; namespaces are safe.

Reading a signature

How do you find out what a function takes? You ask it.

help(round)
Help on built-in function round in module builtins:

round(number, ndigits=None)
    Round a number to a given precision in decimal digits.

    The return value is an integer if ndigits is omitted or None.  Otherwise
    the return value has the same type as the number.  ndigits may be negative.

round(number, ndigits=None) says it all: a number first, then optionally a second argument called ndigits. The = None means you may leave this one out.

Tip

That line is the signature — what goes in, in what order, and what comes back. Read it and you can use a function you have never seen before.

Note

The explanation underneath it is the function’s docstring: text between triple quotes at the top of the function, which help reads back to you. The other kind of note is a # comment — everything after a # on a line is ignored by Python, and is there only for whoever reads the file next. Both are for humans; only one of them answers help.

Catching what comes back

round(mean(readings), 1)
print("and now?")
and now?

The value was computed, and thrown away. A function hands you something; if nobody catches it, it is gone.

average_bpm = round(mean(readings), 1)
print(average_bpm)
100.2

Caution

average_bpm = ... is the catch. Units in the name, so that the next person — you, in three weeks — knows what is inside it.

DIAGNOSE: did it do what I expected?

readings = [78, 82, 0, 104,
            110, 100, 96, 0,
            300, 132]

Not is this number clinically sensible — that is VALIDATE, and it comes later. This is narrower and sharper: given this input, is this the output the function promised?

Start with something you can do in your head. mean of [100, 102] must be 101. Obvious here — not obvious at all for the functions we are about to order.

print(mean([100, 102]))
101

Note

Someone decided that an empty recording is an error rather than a zero, and wrote that decision into statistics. Every function has edges, and someone chose where they are.

Errors are an answer too

mean([]) stopped the program. Was that a flaw?

No — it is the right behaviour. An empty recording has no mean, and quietly returning 0.0 would be far worse: a number nobody chose, travelling into a report.

Errors come in families, and the name tells you the kind of problem:

ValueError the right type of thing, but an impossible value
TypeError the wrong type of thing altogether
ZeroDivisionError the arithmetic cannot be done
FileNotFoundError, ModuleNotFoundError something that should be there is not
StatisticsError what mean([]) raised: statistics defines its own

There are dozens more, and any module may define its own. You are not expected to know them: read the last line of the message, which names the error and says what it objected to.

Note

When you specify a function, the errors are part of the contract: if there are no valid readings, raise a ValueError. You are deciding how it fails, not only how it works.

When you have a plan: try / except

from statistics import mean, StatisticsError

recording = []

try:
    average = mean(recording)
    print("average:", average)
except StatisticsError:
    print("empty recording — nothing to average, moving on")
empty recording — nothing to average, moving on

try runs the risky line. except catches one named kind of failure, and says what to do instead.

Warning

Only catch what you have a plan for. Catching an error you cannot handle is worse than letting the program stop: it carries on with a number nobody chose — a silent failure, built by hand.

What we have just done

from statistics import mean

readings = [78, 82, 0, 104, 110, 100, 96, 0, 300, 132]   # the data
average_bpm = round(mean(readings), 1)                   # a step
print(average_bpm)                                       # look at it

And the checking, in the same programmatic form:

print(mean([100, 102]))     # something I can do in my head: expect 101
print(mean([]))             # an edge: error, and I know why

Important

Data, a step, a result, a check. That is a program. Not one line of it was written by us, and we can defend every line of it.

When the function does not exist

The step we actually need

What percentage of the valid recording time was spent above 100 bpm?

Note

Seven valid readings; the two dropped samples and the artefact are not part of the recording. Three of the seven are above the line — and the one sitting exactly on it is not. 42.9 %

SPECIFY: write the signature first

No module has this function. It is our problem, not Python’s — so we say what the box looks like before anyone writes it.

percent_above(readings, limit_bpm)
  • the name — a verb and the thing it gives back, not process or do_it
  • the inputs — how many, in what order, named with their units
  • what comes back — one number, a percentage from 0 to 100

Written in full, both halves are visible in the file itself:

def percent_above(readings: list, limit_bpm: float) -> float:
    """Percentage of the valid readings above limit_bpm (0-100, one decimal)."""

-> float is the return annotation: what comes out. The docstring says the rest — the units, the range, and what happens at the edges.

Caution

limit_bpm, not limit. A good share of the accidents in engineering software are a number in the wrong units arriving somewhere that never asked.

SPECIFY: the prompt is the signature, plus the decisions

Write a Python function percent_above(readings, limit_bpm).

readings is a list of heart rates in bpm; a reading of 0 means a dropped sample and anything above 250 bpm is an artefact — neither is part of the recording. limit_bpm is the limit in bpm; a reading exactly equal to it does not count as above.

Return the percentage of the remaining readings that are above the limit, rounded to one decimal. If there are no valid readings, raise a ValueError.

Give the function type hints and a docstring stating the units. Plain Python, no packages.

Note

Everything the machine could otherwise decide for itself, we have decided: the zeros, the artefacts, the boundary, the empty case. That is last week’s lesson, written down — and it is the fence.

Where the body goes

The function does not go in your program. It goes in a file of its own:

# vitals.py

def percent_above(readings, limit_bpm):
    """Percentage of the valid recording time spent above limit_bpm."""
    ...

A .py file full of functions is a module — exactly what statistics is. Ours is called vitals.

Tip

Two files, two jobs. vitals.py holds the work, written to your specification. main.py holds the orchestration: the data, the calls, the checks. You own main.py line by line.

Using your own module

# main.py
import vitals

readings = [78, 82, 0, 104, 110, 100, 96, 0, 300, 132]

percent = vitals.percent_above(readings, limit_bpm=100)
print(percent)
42.9

Identical to mean: a name, brackets, inputs, a value caught on the left. The only difference is who wrote the inside.

Note

limit_bpm=100 names the argument as it is passed: longer to type, impossible to misread, and it survives somebody adding a parameter later.

Where Python looks

When you write import vitals, Python looks:

  1. in your project folder — vitals.py is right there
  2. then in your virtual environment — where the packages you install live
  3. then in Python’s own library — statistics, math, and the rest

ModuleNotFoundError: No module named 'vitals' means it looked in all three and found nothing: usually the file is not where you think, or VS Code has the wrong folder open.

Warning

Importing a file runs it, top to bottom. A stray print at the bottom of vitals.py fires the moment you import it, in the middle of somebody else’s program. Keep modules quiet: definitions only.

DIAGNOSE: checking what came back

An ordinary case is not enough

42.9

Three readings out of the seven valid ones are above the line, and 3/7 is 42.86. So: right — if you count by hand first.

Caution

Ten readings you can count. A real recording has 28,800, and “it looked about right” is not a check.

Start with the edges

The cases where you know what should happen, whatever the data:

print(vitals.percent_above([], 100))              # nothing at all
print(vitals.percent_above([0, 0, 0], 100))       # only dropped samples
print(vitals.percent_above([100, 100], 100))      # all exactly on the limit

The first two must raise ValueError — we asked for that. The third must be 0.0, because exactly 100 does not count as above.

Note

You already decided all three when you wrote the prompt. Checking them is checking that the machine kept to the fence.

An error you asked for is a result, so it can be checked like one:

try:
    vitals.percent_above([], 100)
    print("NO ERROR — the fence is broken")
except ValueError:
    print("ok: an empty recording is refused")

assert: say it once, check it forever

above = 6
total = 20
assert abs(100 * above / total - 30.0) < 0.05
print("still here")
still here

assert takes a condition — true or false, like an if — and does nothing at all when it is true.

assert abs(100 * above / total - 25.0) < 0.05
---------------------------------------------------------------------------
AssertionError                            Traceback (most recent call last)
Cell In[13], line 1
----> 1 assert abs(100 * above / total - 25.0) < 0.05

AssertionError:

Important

Loud when wrong, silent when right. And note what we did not write: no == between two decimals. Week 2: 0.1 + 0.2 == 0.3 is False. Always compare numbers with a tolerance.

The strongest check: build the data yourself

Instead of computing the answer from the data, build data whose answer you already know.

Twenty readings, of which exactly six are above the limit. Whatever happens inside the box, it must say 30.0.

known = vitals.make_readings(n_total=20, n_above=6, limit_bpm=100)
assert abs(vitals.percent_above(known, limit_bpm=100) - 30.0) < 0.05

Tip

No counting, no arithmetic, no trust. The answer is a consequence of how the data was made — and it works just as well with twenty readings as with twenty thousand.

The generator is a second fenced job

# vitals.py

def percent_above(readings, limit_bpm):
    """Percentage of the valid recording time spent above limit_bpm."""
    ...

def make_readings(n_total, n_above, limit_bpm):
    """A recording of n_total readings, n_above of them above the limit."""
    ...

Same procedure: a signature you write, a prompt you write, a body the machine writes. It lives in the module beside the step it tests.

Note

Your orchestrator stays clean: data, steps, results, checks. Nothing in main.py ever needs a loop.

The whole program

import vitals

# --- checks first, on data we built
known = vitals.make_readings(n_total=20, n_above=6, limit_bpm=100)
assert abs(vitals.percent_above(known, limit_bpm=100) - 30.0) < 0.05
assert abs(vitals.percent_above(vitals.make_readings(10, 10, 100), 100) - 100.0) < 0.05
assert abs(vitals.percent_above(vitals.make_readings(10, 0, 100), 100) - 0.0) < 0.05
print("all checks passed")

# --- only now, the real recording
readings = [78, 82, 0, 104, 110, 100, 96, 0, 300, 132]
percent = vitals.percent_above(readings, limit_bpm=100)
print("above 100 bpm:", percent, "% of the valid time")

Important

Checks before results. If the checks fail, the number underneath them is not worth printing.

Warning

Notice what an assert can and cannot do. It compares values: this input gives that number. It is clumsy for anything else — did the function change my list, does it refuse bad input, does it still work on the ten-thousandth call. Those need a proper testing tool, which is where next week starts.

When a check fails, what is wrong?

Three candidates, and only one of them is the code:

the specification you never said what should happen in this case
the call you passed the wrong thing, in the wrong order, or in the wrong units
the body the machine built something that does not match what you asked for

Important

Say which one you think it is before you ask for a fix. Otherwise you are just shaking the box.

The loop, from now on

  1. Decide the step: what goes in, what comes out
  2. SPECIFY: the signature, with units in the names, and the decisions nobody else should make
  3. Order the body, and put it in the module
  4. DIAGNOSE: edges, then data you built, as assert lines
  5. Then run it on the real data
  6. If something fails: specification, call, or body?

Tip

Everything you decided in the prompt is a fence. If you find yourself repeating the same fences in every prompt — units, no extra packages, do not change my signature — that is exactly what a project rules file is for, and we will come back to it.

Tutorial

  1. Set up: one folder, one .venv, main.py and an empty module beside it
  2. Together: build the orchestrator for a new recording — data, len, mean, median, and what each one is worth
  3. SPECIFY one step: the signature, then the prompt; put the body in the module and import it
  4. DIAGNOSE it: the edges first, then a generator, then the assert lines
  5. Break it on purpose: change one thing in the call, and say which of the three is now wrong

Take-home message

  • A function is a fence: the machine works inside it, you work outside it
  • A signature is the whole contract — names, order, units, what comes back
  • import brings in a module, Python’s or your own: the body lives there, the orchestration lives in main.py
  • A result nobody catches is gone; a result nobody checks is a rumour
  • The strongest check is on data you built, because then you knew the answer before you asked
