What is a file

The same recording, as the device wrote it

The wearable from weeks 2 and 3 does not hand you a Python list. It writes this, recording.csv:

# WristHR export
# firmware 2.1
time_s,hr_bpm
0,78
15,82
30,
45,104
60,110
75,100
90,96
105,
120,300
135,132

Two lines of notes, a header naming the columns (with units), then one reading per line.

The dropped samples are not 0 here: they are empty. The device made that decision, not you.

Note

CSV: comma-separated values. The commonest data format in science, and the least defined — every device has its own idea of what goes between the commas.

Underneath, a file is a row of bytes

VS Code shows you text. The disk holds numbers from 0 to 255, one after another, with a name attached.

with open("data/recording.csv", "rb") as file:      # "rb": read the raw bytes
    print(file.read()[:40])
b'# WristHR export\n# firmware 2.1\ntime_s,h'

The b'...' means bytes. \n is one byte: the end of a line. (Files written on Windows often end each line with two, \r\n; Python hides the difference when you read text.)

Tip

Text is bytes plus an agreement about which number means which character. The agreement is called the encoding.

What an encoding is

Every character is stored as a number. Here is one line of our file:

print(list("hr,78\n".encode("ascii")))
[104, 114, 44, 55, 56, 10]
character h r , 7 8 \n
byte 104 114 44 55 56 10

Note

The heart rate 78 is not stored as the number 78. It is two characters, 7 (55) and 8 (56). In a text file, numbers are text.

A short history of the agreement

  • ASCII (1960s): 7 bits, 128 characters. English letters, digits, punctuation. No é, no °, no µ.
  • 8 bits, 256 characters: the spare 128 were filled in differently in every region — Latin-1, Windows cp1252, Cyrillic, Greek… Same byte, different character.
  • Unicode and UTF-8: one list for every character in every language (about 150,000), stored in 1 to 4 bytes each. The first 128 are ASCII, unchanged.
for symbol in ["°", "µ", "€"]:
    print(symbol, symbol.encode("cp1252"), symbol.encode("utf-8"))
° b'\xb0' b'\xc2\xb0'
µ b'\xb5' b'\xc2\xb5'
€ b'\x80' b'\xe2\x82\xac'

Tip

Plain English letters and digits look the same in every encoding. The trouble starts with the first °, µ or accented name — exactly what scientific files are full of.

When the agreement is broken

UTF-8 bytes, read back as Windows cp1252:

temperature = "37.2 °C"
raw = temperature.encode("utf-8")
print(raw)
print(raw.decode("cp1252"))
b'37.2 \xc2\xb0C'
37.2 Â°C

Warning

No error. A unit quietly became Â°C, and it will travel into your plot labels and your report.

The other way round — a file written by a Windows device, read as UTF-8:

raw = "37.2 °C".encode("cp1252")
print(raw.decode("utf-8"))
---------------------------------------------------------------------------
UnicodeDecodeError                        Traceback (most recent call last)
Cell In[4], line 2
      1 raw = "37.2 °C".encode("cp1252")
----> 2 print(raw.decode("utf-8"))

UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb0 in position 5: invalid start byte

Important

UnicodeDecodeError is one of the commonest errors you will meet with real data. It is a data failure, not a bug in your code: the file is not in the encoding you said. Look at the file (VS Code shows its encoding in the bottom-right corner), then say the right one: encoding="cp1252". And always say it — on Windows the default may not be UTF-8.

Text files and binary files

text — .csv, .txt, .json, .md, .py the bytes are characters; any editor can show them, and you can check them by eye
binary — images, .xlsx, .h5, .mat the bytes mean something only to a program that knows the format

Today: text. Next week: a binary format built for science, HDF5, and the package that reads it.

Caution

Never edit raw data in Excel and save over it. Open, save — and decimal commas, dates and long numbers may come back changed. Raw data is read-only: work on a copy.

Where is the file

A path is an address

"C:/Users/ab123c/ENG2012/week4/data/recording.csv"     # absolute: from the top of the disk
"data/recording.csv"                                   # relative: from... where?

A relative path starts from the working directory: the folder Python was run from — not the folder the script lives in.

from pathlib import Path
print(Path.cwd())          # ask, don't guess

Note

Week 1, again: FileNotFoundError from the wrong folder. Open the project folder in VS Code, run from there, and every relative path in this course works.

Windows, and the backslash

print("C:\temp\new.csv")
C:  emp
ew.csv

Inside a Python string, \t is a tab and \n is a new line. The path was destroyed before open ever saw it — and "C:\Users\..." does not even run: \U starts a special character code, and Python stops with a SyntaxError.

Two ways out, both fine on Windows:

from pathlib import Path
print("C:/temp/new.csv")                 # forward slashes work everywhere
print(Path("data") / "recording.csv")    # or let Python build the path
C:/temp/new.csv
data\recording.csv

Reading a file

with open(...)

with open("data/recording.csv", encoding="utf-8") as file:
    text = file.read()
  • the path — where it is
  • the mode — left out here, so "r": read text
  • the encoding — the agreement, said out loud

Tip

with closes the file when the indented block ends — even if something inside it fails. A file left open can stay locked, half-written, or both.

What comes back is text, not numbers

with open("data/recording.csv", encoding="utf-8") as file:
    lines = file.read().splitlines()        # one string per line of the file

print(lines[3])
time_text, hr_text = lines[3].split(",")
print(hr_text * 2)
0,78
7878

The first reading, doubled, is 7878 bpm. Week 2: * on a string repeats it. Everything that comes out of a text file is a string until you say otherwise.

The whole second column, exactly as read from the file. What was the highest heart rate of the night?

hr_texts = ["78", "82", "", "104", "110", "100", "96", "", "300", "132"]
print(max(hr_texts))
96

Warning

No error, and wrong. Text is compared letter by letter, like words in a dictionary: "9" comes after "3" and "1", so "96" beats "300" and "132". The conversion is a step, and it must happen before any arithmetic: float(hr_text).

Not every CSV uses commas

Where the comma is the decimal separator — most of Europe — spreadsheets export with semicolons. Other devices use tabs (TSV), or spaces. The extension .csv promises nothing: look at the file.

line = "0;72,5"                          # one line from an Italian Excel export
time_text, hr_text = line.split(";")
print(float(hr_text.replace(",", ".")))
72.5

Now split it on the separator you assumed:

time_text, hr_text = line.split(",")
print(time_text, "|", hr_text, "->", float(hr_text), "bpm")
0;72 | 5 -> 5.0 bpm

Warning

Two pieces, as expected, so nothing complains — and the heart rate is 5 bpm. The wrong separator is a data failure that looks like a result.

When the separator is inside a value

A field that contains the separator is wrapped in quotes — a note typed by a nurse, a patient’s name:

line = '0,78,"walking, then stairs"'
print(line.split(","))
['0', '78', '"walking', ' then stairs"']

split knows nothing about quotes. The csv module does — it comes with Python, nothing to install:

import csv
print(next(csv.reader([line])))          # one line here; on a file it reads every line
['0', '78', 'walking, then stairs']

Tip

split, strip and float are enough for a tidy column of numbers like our wristband’s. For anything messier, put it in the prompt: use the csv module from the standard library, with delimiter ';'. Quotes, separators and empty fields are then handled by code that has been tested for thirty years.

The loader is a step: a fence, a prompt, a body

def load_recording(path) -> list:
    """Load heart rates (bpm) from a wearable export file."""

Same procedure as percent_above: you write the signature and the decisions, the machine writes the body.

  • what to skip: the # notes, the header, blank lines
  • what a dropped sample becomes
  • what comes back: a list of floats, in bpm, in file order
  • what happens if the file is not there

Important

This is where the data decisions live. Every one you leave out, the machine makes for you — on a file it has never seen.

Where the prompt lives

From today, the prompt that produced a function sits right above it, word for word.

What you asked for — the # PROMPT block, yours

# PROMPT (final version used):
# Write a Python function load_recording(path)
# that reads a heart-rate file exported by the
# wearable. Lines starting with '#' are notes from
# the device and are skipped. The first other line
# is the header 'time_s,hr_bpm'. Every line after
# it is a time in seconds and a heart rate in bpm,
# separated by a comma. An empty heart rate means
# a dropped sample: return it as 0, because that
# is what percent_above expects. Return the heart
# rates as a list of floats, in file order.
# Open the file with encoding="utf-8". If the file
# does not exist, let the FileNotFoundError happen.
# Type hints and a docstring stating the units.
# Plain Python, no packages.

What the function promises — the signature and docstring, the machine’s, checked by you

def load_recording(path) -> list:
    """Load heart rates (bpm) from a
    wearable export file.

    Lines starting with '#' are skipped,
    as is the 'time_s,hr_bpm' header.
    An empty heart-rate field is a
    dropped sample and is returned as 0.0.
    Returns a list of floats in bpm,
    in the order they appear in the file.
    """

Note

Read them side by side: every decision on the left should appear on the right. One missing is a question to ask before you use the function.

Caution

Only the final prompt goes in the file; the earlier attempts stay in the transcript. Assistants love tidying comments: tell yours never to edit or remove a # PROMPT block — and check that it did not.

Reading the body it wrote

Week 2’s four things: the signature, the guards, the branch, the state.

def load_recording(path) -> list:
    """..."""
    readings_bpm = []
    header_seen = False
    with open(path, encoding="utf-8") as file:
        for line in file:
            line = line.strip()
            if line == "" or line.startswith("#"):
                continue
            if not header_seen:
                header_seen = True
                continue
            time_text, hr_text = line.split(",")
            if hr_text == "":
                readings_bpm.append(0.0)
            else:
                readings_bpm.append(float(hr_text))
    return readings_bpm

Tip

strip trims spaces and the end-of-line from both sides; continue means skip the rest of this turn of the loop, go to the next line. You do not need to write this — you need to be able to point at where each decision in your prompt ended up.

Why 0, and not “nothing”?

Line 6 of the file is 30, — a time, and no heart rate. What should the loader put in the list?

Suppose the prompt had said nothing, and the machine chose None — Python’s word for no value. A perfectly reasonable choice. Load the file, then hand the list to last week’s step:

readings = vitals.load_recording("data/recording.csv")
print(readings[:4])
vitals.percent_above(readings, limit_bpm=100)
[78.0, 82.0, None, 104.0]
Traceback (most recent call last):
  ...
  File "vitals.py", line 65, in percent_above
    if hr != 0 and hr <= 250:
TypeError: '<=' not supported between instances of 'NoneType' and 'int'

Neither function is wrong on its own. percent_above was specified last week to expect 0 for a dropped sample; the loader hands it None. The loader’s output is the next step’s input, and the two disagree.

Important

That is a specification / interface failure: the glue between two steps. It is why the prompt says return it as 0, because that is what percent_above expects. Loud this time. In week 6 you will chain three steps, and not every disagreement will be loud.

The orchestrator, now

The same 42.9 as last week — the same recording, as the device actually wrote it. Swap the file name and it runs on tonight’s recording, or on 28,800 readings.

Writing a file

Mode "w"

with open("summary.txt", "w", encoding="utf-8") as file:
    file.write(f"above 100 bpm: {percent} % of the valid time\n")
  • write takes text only: numbers go in through an f-string
  • write adds no end-of-line: the \n is yours

Warning

"w" empties the file the moment it opens — before you write anything, and without asking. Point it at your raw data by mistake and the recording is gone.

Three modes, three intentions

mode if the file exists if it does not
"w" emptied, then written created
"a" added to, at the end created
"x" refuses: FileExistsError created

Tip

For anything you would hate to lose, "x" is a fence: it turns a silent disaster into a loud error. Writing results is a decision, and the mode is where you write it down.

pytest: the checks get their own file

Why move the checks

Week 3’s main.py did two jobs: it checked, then it worked.

  • every run of the real job re-ran every check
  • a failed assert stopped at the first problem, and hid the rest
  • checking that an error is raised took five lines of try/except

From today: main.py does the job. test_vitals.py proves the job is done right. A tool, pytest, runs the proof.

Note

pytest is not part of Python. Install it into your venv, once: python -m pip install pytest. It is your first package from outside — the full story is next week.

A test is a function whose name starts with test_

# test_vitals.py
import pytest
import vitals


def test_known_file_20_6():
    """Made by make_fixtures.py: 20 readings, 6 above 100 -> 30.0 %."""
    readings = vitals.load_recording("data/known_20_6.csv")
    assert vitals.percent_above(readings, limit_bpm=100) == pytest.approx(30.0)

Still an assert. The only new thing is pytest.approx(30.0): equal, within a sensible tolerance — last week’s abs(... - 30.0) < 0.05, said in words.

Tip

The name says what is being checked; the docstring says where the expected value came from. A stranger should be able to tell why 30.0 is right without running anything.

Checking that it refuses

Last week, five lines:

try:
    vitals.percent_above([0, 0, 0], 100)
    print("NO ERROR — the fence is broken")
except ValueError:
    print("ok: an empty recording is refused")

This week, two:

def test_empty_recording_is_refused():
    """No valid readings -> ValueError, as the prompt says."""
    with pytest.raises(ValueError):
        vitals.percent_above([0, 0, 0], limit_bpm=100)

Note

Inside this block, a ValueError must happen. If it does, the test passes. If nothing goes wrong, the test fails — the fence is broken.

Running it

From the project folder, in the terminal:

python -m pytest
============================= test session starts ==============================
collected 7 items

test_vitals.py .......                                                   [100%]

============================== 7 passed in 0.02s ===============================

pytest finds every file called test_*.py, runs every function called test_* inside it, and prints one dot per test that passed.

Tip

python -m pytest, like python -m pip: the python of your venv runs it, so it sees exactly the packages your program sees. It is also, word for word, what the marker will type.

collected 0 items

Warning

No red, no error — and nothing was checked. pytest only runs what it can find: files called test_*.py, functions called test_*. Read the count: 7 passed is evidence; the absence of red is not.

Who writes what, in the test file

you the file, the test names, and the expected values in the docstrings — by hand, or known by construction
the assistant the bodies — in a separate chat, without vitals.py in sight

Caution

Tests written by an assistant that can see the code tend to check what the code does, not what it should do. Then they pass by construction, and prove nothing.

Building the test file, step by step

# test_vitals.py — the skeleton you write

# PROMPT (final version used, sent in a new chat,
# without vitals.py):
# I am testing a module called vitals with pytest.
# Write the bodies of the test functions below.
# Use only the expected values I give in each
# docstring; do not compute them, do not import
# anything except pytest and vitals, and do not
# change the names.
import pytest
import vitals


def test_known_file_20_6():
    """Made by make_fixtures.py: 20 readings,
    6 above 100 -> 30.0 %."""
    assert False, "body not written yet"


def test_empty_recording_is_refused():
    """No valid readings -> ValueError,
    as the prompt for percent_above says."""
    assert False, "body not written yet"
  1. New File in VS Code: test_vitals.py, in the same folder as vitals.py
  2. The two imports, then one function per check: a name starting test_, and a docstring saying what goes in, what must come out, and where that value came from
  3. Every body: assert False, "body not written yet". Run python -m pytest — all red. Right: nothing is proven yet
  4. Open a new chat; send the # PROMPT and this file, not vitals.py
  5. Replace each assert False with the body that comes back; keep your names, docstrings and # PROMPT block
  6. python -m pytest, and read the count

Warning

Why not leave the body empty, ...? Because a test with an empty body passes. It checks nothing, and the count says passed anyway.

When a test fails, what is wrong?

Last week, three candidates. Files add a fourth:

the specification you never said what should happen in this case
the call wrong thing, wrong order, wrong units — or the wrong path
the body the machine built something that does not match what you asked for
the file the data is not what you assumed: a different separator, an extra column, a note in the middle

Important

Say which one you think it is before you ask for a fix. The last one is never fixed by changing the code until you have looked at the file.
