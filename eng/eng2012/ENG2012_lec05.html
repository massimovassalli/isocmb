Key → value

A dictionary keeps every value next to a name (its key):

record = {
    "subject_id": "S01",
    "device": "wristband",
    "units": "bpm",
    "interval_s": 15.0,
    "hr_bpm": [78.0, 82.0, 0.0, 104.0, 110.0, 100.0, 96.0, 0.0, 300.0, 132.0],
}
print(record["device"])
print(record["interval_s"], "s")
print(record["hr_bpm"][:4])
wristband
15.0 s
[78.0, 82.0, 0.0, 104.0]

Tip

Curly brackets { }, pairs written key: value, separated by commas. You get a value by its name, in square brackets — not by its position, as in a list.

Asking for a key that is not there

print(record["unit"])
---------------------------------------------------------------------------
KeyError                                  Traceback (most recent call last)
Cell In[42], line 1
----> 1 print(record["unit"])

KeyError: 'unit'

Note

A misspelt key fails at once, and loudly, naming the key it could not find. Compare a list, where readings[3] happily gives you a number whether or not it is the one you meant.

Asking first, without failing:

print("units" in record, "unit" in record)
print(sorted(record))          # the keys, in alphabetical order
print(len(record))             # how many pairs
True False
['device', 'hr_bpm', 'interval_s', 'subject_id', 'units']
5

A value can be anything

key value type
"subject_id" "S01" text
"device" "wristband" text
"units" "bpm" text
"interval_s" 15.0 a number
"hr_bpm" [78.0, 82.0, ...] a whole list

The keys are usually text; the values can be numbers, text, lists — even other dictionaries. One record holds a recording and everything you need to know to use it.

Caution

A dictionary can be changed after it is made: record["interval_s"] = 30 silently replaces the value. Like "w" last week, convenient and dangerous: a step that receives a record should read it, not rewrite it.

For the curious: what can be a key?

Anything hashable — anything Python can turn into a fixed fingerprint, which means a value that cannot change. Numbers, text, tuples, even functions:

odd = {42: "a number", (1, 2): "a tuple", len: "a function"}
print(odd[len])
a function

A list can change, so it cannot be a key:

{[1, 2]: "a list"}
---------------------------------------------------------------------------
TypeError                                 Traceback (most recent call last)
Cell In[45], line 1
----> 1 {[1, 2]: "a list"}

TypeError: unhashable type: 'list'

Note

Not something you will need in this course. But it explains an error message you may meet one day: TypeError: unhashable type: 'list'.

The record is the interface

Week 4: the loader returned None for a gap, percent_above expected 0, and two correct functions disagreed. With a record, the agreement between steps can be written down and checked:

key type units meaning
"subject_id" str — as in the study
"device" str — which device recorded it
"units" str — the units of hr_bpm
"interval_s" float s time between two readings
"hr_bpm" list of float bpm the readings; 0.0 = dropped sample 
print(set(record) == {"subject_id", "device", "units", "interval_s", "hr_bpm"})
True

Important

This table is a specification: what goes out of one step, and into the next. Next year, in ENG3090, every step of every pipeline starts with exactly this — what goes IN, what comes OUT, with types and units.

You have seen this before: JSON

The same key → value idea, written as text, is the most common format for exchanging data on the internet:

import json
print(json.dumps({"subject_id": "S01", "device": "wristband", "interval_s": 15.0}, indent=2))
{
  "subject_id": "S01",
  "device": "wristband",
  "interval_s": 15.0
}

Text file, readable by eye, json in the standard library. Keep the shape in mind: you are about to see it again, inside a scientific data format.

Thirty patients, two devices, two sampling intervals. As CSV files:

The metadata ends up in the file names — typed by hand, abbreviated differently by everyone, and lost the moment someone renames a file.

Tip

What we want: every recording with its labels attached, all in one place, reachable by key — a dictionary of records, on disk.

Zarr: a study in one folder

data/ward4.zarr is a folder. Inside, one group per subject, and in each group an array:

ward4.zarr/
├── zarr.json          study, note
├── S01/
│   ├── zarr.json      device
│   └── hr_bpm/
│       ├── zarr.json  units, interval_s
│       └── c/0        the readings
├── S02/
│   └── ...
└── S03/
    └── ...
  • a group is like a dictionary: it holds things by name (S01, hr_bpm)
  • an array holds the numbers
  • every group and every array carries attributes: a small dictionary of labels
  • every one of them has its own zarr.json, always with that name: what it is, and its labels

Note

S01/hr_bpm is a key, written like a path. Zarr’s whole design is a dictionary from keys to stored pieces — on your disk today, and just as well on a server in the cloud.

The labels are text you can read

Open ward4.zarr/S01/hr_bpm/zarr.json in VS Code (shortened):

{
  "shape": [10],
  "data_type": "float64",
  "fill_value": 0.0,
  "codecs": [ ... "zstd" ... ],
  "attributes": {
    "interval_s": 15,
    "units": "bpm"
  },
  "zarr_format": 3,
  "node_type": "array"
}

JSON: how many values, their type, how they were compressed — and the attributes, the labels that the CSV kept in # comments.

The readings themselves are in c/0: binary, and compressed. Open it and you see nonsense.

Tip

Week 4’s table had text files and binary files. Zarr is both: the labels as text, so you can check them by eye; the numbers as binary, so millions of them stay small and fast.

Opening the store

Three subjects; ten, fifteen and twelve readings; numbers stored as float64 — decimals, 8 bytes each.

How Zarr reads 54 bytes of nonsense

S01/hr_bpm/c/0 is 54 bytes on disk. Ten readings of 8 bytes each would be 80. Everything needed to turn one into the other is written in the zarr.json beside it:

zarr.json says so Zarr knows
"codecs": [... "zstd" ...] the bytes are compressed: decompress first (54 → 80 bytes)
"data_type": "float64" every 8 bytes are one decimal number
"endian": "little" in which order the 8 bytes of a number are written
"shape": [10], "chunk_shape": [10] how many numbers there are, and how many live in this piece

Note

The binary part is meaningless on its own; the text part is the agreement that makes it readable — last week’s encoding, for numbers. The type is never guessed: it is written down, once, next to the data. A big recording is cut into several pieces (c/0, c/1, …), and a program can read just the one it needs.

print(hr.shape, hr.dtype)
wristband

(10,) float64

The order is not promised

Warning

A dictionary of subjects is reached by name, not by position. The order you get them in is whatever the folder listing happened to give. If your report must list S01 first, someone has to decide that — sorted(...) — and the prompt is where you say so.

Modes: the fence, again

mode if the store exists if it does not
"r" read only: writing raises ValueError FileNotFoundError
"a" read and add created
"w-" refuses: FileExistsError created
"w" the whole study is deleted, then written created

Important

Week 4’s "w" emptied one file. Zarr’s "w" empties a folder: thirty patients, gone, without a question. Raw data is opened with mode="r", always — and that goes in the prompt.

What comes back is an array

ward4.zarr/
├── S01/
│   └── hr_bpm/     ← hr
│       ├── zarr.json
│       └── c/0
...

hr = root["S01/hr_bpm"] is the array itself: its labels, its shape, its type. The numbers stay on disk until you ask for them:

print(hr[:])           # [:] means: all of it
array([ 78.,  82.,   0., 104., 110., 100.,  96.,   0., 300., 132.])

Not a list: a numpy array. Zarr does not do arithmetic itself; it is built on top of numpy, the package almost every piece of scientific Python stands on. You did not ask for numpy. It came anyway — more on that shortly.

numpy, enough to read it

Same numbers, different behaviour

import numpy as np

hr_list = [78.0, 82.0, 0.0, 104.0]
hr_array = np.array(hr_list)

print(hr_list * 2)
print(hr_array * 2)
[78.0, 82.0, 0.0, 104.0, 78.0, 82.0, 0.0, 104.0]
[156. 164.   0. 208.]
print(hr_list + [1.0])
print(hr_array + 1.0)
[78.0, 82.0, 0.0, 104.0, 1.0]
[ 79.  83.   1. 105.]
print(hr_list == 0)
print(hr_array == 0)
False
[False False  True False]

Note

A list is a container: * repeats it, + glues lists together, == compares the whole thing. An array is a vector: every operation applies to every element.

Why arrays exist: speed

Counting the readings above 100 bpm in one million samples — a loop, and numpy:

import timeit

night = np.random.default_rng(0).uniform(40, 180, 1_000_000)

def count_loop():
    n = 0
    for hr in night:
        if hr > 100:
            n += 1
    return n

def count_numpy():
    return int((night > 100).sum())

t_loop = min(timeit.repeat(count_loop, number=1, repeat=5))     # best of five runs
t_np = min(timeit.repeat(count_numpy, number=1, repeat=5))
print(f"loop: {1000 * t_loop:.0f} ms   numpy: {1000 * t_np:.1f} ms   ~{t_loop / t_np:.0f} times faster")
loop: 62 ms   numpy: 0.8 ms   ~78 times faster

Tip

One reading per second for twelve days is a million samples. numpy runs the loop in compiled code, not in Python. You will not write this — but you will read code that does, from every assistant.

Two traps worth knowing by sight

print((hr_array > 60) and (hr_array < 100))
---------------------------------------------------------------------------
ValueError                                Traceback (most recent call last)
Cell In[52], line 1
----> 1 print((hr_array > 60) and (hr_array < 100))

ValueError: The truth value of an array with more than one element is ambiguous. Use a.any() or a.all()

Python’s and wants one True or False; an array holds many. Element by element needs &, each condition in brackets:

print((hr_array > 60) & (hr_array < 100))
[ True  True False False]

The same thing inside a test:

assert hr_array == [78.0, 82.0, 0.0, 104.0]
---------------------------------------------------------------------------
ValueError                                Traceback (most recent call last)
Cell In[54], line 1
----> 1 assert hr_array == [78.0, 82.0, 0.0, 104.0]

ValueError: The truth value of an array with more than one element is ambiguous. Use a.any() or a.all()

Note

The fix used in today’s loader: hand the next step a plain list — hr[:].tolist() — because the steps from weeks 3–4 were specified for a list. That is an interface decision, and it goes in the prompt.

The type of a number is a decision

A cheaper wristband stores every heart rate in one byte (uint8: whole numbers from 0 to 255), to save memory. Our night has an artefact at 300:

night = np.array([78, 82, 0, 104, 110, 100, 96, 0, 300, 132])
print(night.astype(np.uint8))
[ 78  82   0 104 110 100  96   0  44 132]
print(np.array([78, 82, 300], dtype=np.uint8))
---------------------------------------------------------------------------
OverflowError                             Traceback (most recent call last)
Cell In[56], line 1
----> 1 print(np.array([78, 82, 300], dtype=np.uint8))

OverflowError: Python integer 300 out of bounds for uint8

Warning

Same value, two behaviours. From a list: a loud OverflowError. From an array: 44 — no error, and 44 bpm is a believable heart rate, so the artefact turns into a bradycardia. Whoever chose the type made a specification decision. Next year, in ENG3090, every image is made of uint8 pixels: this is the same overflow, waiting for you.

The last digit

values = [0.1] * 1000
print(sum(values))
print(np.sum(np.array(values)))
100.0
100.00000000000001

Two correct ways to add the same thousand numbers, two different last digits: they add in a different order, and every addition of decimals rounds.

Tip

Week 2: never == on decimals. Week 4: pytest.approx. Now you know one more reason — the same calculation, done by someone else’s code, need not match yours to the last digit.

The loader is a step, again

load_subject: the prompt and the promise

# PROMPT (final version used):
# Write a Python function load_subject(store_path,
# subject_id) that opens a Zarr study store with
# zarr version 3 (zarr>=3,<4), read-only (mode="r").
# Each subject is a group with an attribute 'device';
# inside it, an array 'hr_bpm' with attributes
# 'units' and 'interval_s'. Return one dictionary
# with exactly these keys:
#   "subject_id": the id, as given (str)
#   "device":     the group's 'device' attribute (str)
#   "units":      the array's 'units' attribute (str)
#   "interval_s": 'interval_s', as a float
#   "hr_bpm":     the heart rates as a plain Python
#                 list of floats, in order (not a
#                 numpy array: the steps from weeks
#                 3-4 expect a list)
# Dropped samples are stored as 0 and stay 0. If the
# subject is not in the store, let the KeyError
# happen. Type hints and a docstring stating the units.
def load_subject(store_path,
                 subject_id: str) -> dict:
    """Return one subject's record
    from the study store.

    Keys: "subject_id" (str),
    "device" (str), "units" (str),
    "interval_s" (float, seconds
    between readings), "hr_bpm"
    (list of float, heart rates in
    bpm, 0.0 = dropped sample).
    Raises KeyError if the subject
    is not in the store.
    """

Note

The record table from earlier, word for word. Three new lines matter: the version, read-only, and a list, not an array. Each one is a decision someone would otherwise have made for you.

Reading the body it wrote

    root = zarr.open_group(store_path, mode="r")
    group = root[subject_id]
    hr = group["hr_bpm"]
    return {
        "subject_id": subject_id,
        "device": group.attrs["device"],
        "units": hr.attrs["units"],
        "interval_s": float(hr.attrs["interval_s"]),
        "hr_bpm": hr[:].tolist(),
    }

Open read-only; go down the tree by key; build the record, one key per line.

Tip

No loop, no branch: the organisation lives in the data, so the code is short. Point at the line where each decision from the prompt ended up — and ask what happens if a subject has no units attribute. Nobody decided. Hold that thought until the assignment.

Other people’s code changes

You ask an assistant for a function that opens the store. It answers with:

store = zarr.DirectoryStore("data/ward4.zarr")
root = zarr.open_group(store=store, mode="r")
AttributeError: module 'zarr' has no attribute 'DirectoryStore'

Not a hallucination: this was correct for zarr 2. Zarr 3 (2025) reorganised its functions, and assistants have read far more zarr 2 code than zarr 3.

Important

Which of the four is it? Not the specification, not your call, not the file: the body was written for another environment. The fix is to say the version — in the prompt (zarr version 3), and in the project, so that everyone who runs it gets the same one.

requirements.txt

A text file, in the project folder, one package per line:

# The packages this project needs, installed with:
#     python -m pip install -r requirements.txt
pytest>=9
zarr>=3,<4
line means
zarr any version — whatever is newest today
zarr>=3,<4 any zarr 3: the version the code was written for
zarr==3.4.1 exactly this one

Note

python -m pip freeze prints every package in the venv with its exact version — numpy and all the others that came along included. Saved as requirements.txt, it reproduces the environment exactly:

python -m pip freeze > requirements.txt

> sends what the command prints into a file — and, like "w", replaces the file if it exists. Either way, the project is now tidy and redistributable: the code, the data, and what it needs to run.

The clean rebuild

“It works on my machine” is an environment failure that has not happened yet. Find it before anybody else does:

  1. a new, empty folder; unzip your project into it
  2. python -m venv .venv, select the interpreter
  3. python -m pip install -r requirements.txt
  4. python -m pytest — and read the count
  5. python main.py

Important

This is, word for word, what the marker does with your submission. A package you installed by hand weeks ago and forgot to list, a file you referred to on your desktop, a folder name that only exists on your laptop: all of them fail here — in your hands, not in the marker’s.

Tip

You will meet HDF5 in other people’s data; for your own, Zarr is the more future-proof choice. To email a Zarr store, zip the folder. And the concepts are the same, so what you learn today reads both.

Databases (beyond this course)

When there are many records with the same fields, and the questions run across them — which subjects were recorded with the strap, at 30 s? — data goes into a database, often on a server you query remotely.

SELECT subject_id
FROM recordings
WHERE device = 'chest strap' AND interval_s = 30;

SQL says what you want, never how to find it: the database decides the how. A query is a specification. (sqlite3, a small database in a single file, is even in Python’s standard library.)

Note

Out of scope for this course — but every hospital record system you will work with is one.

Take-home message

  • A list of numbers forgets what they mean. A record keeps the meaning next to the numbers: key → value
  • The record’s keys, types and units are the interface between steps — written down, and tested
  • Zarr is the same idea on disk: groups, arrays, attributes; the labels readable by eye
  • Raw data is opened read-only: mode="r". Zarr’s "w" deletes a whole study
  • numpy arrays behave differently from lists: *, ==, and, and the type of a number is a decision

You have been using objects since week 4

Each time: a value, a dot, and a function or a property that belongs to it and works on that value’s own contents. A value that carries its own functions and its own state is an object; the recipe that makes objects of one kind is a class.

A dictionary that carries its own functions

class Recording:
    """One subject's recording: the data of a record, plus functions that act on it."""

    def __init__(self, record: dict):
        self.subject_id = record["subject_id"]       # the state: what this
        self.interval_s = record["interval_s"]       # recording knows
        self.hr_bpm = record["hr_bpm"]               # about itself

    def duration_min(self) -> float:
        return len(self.hr_bpm) * self.interval_s / 60

    def percent_above(self, limit_bpm: float) -> float:
        return vitals.percent_above(self.hr_bpm, limit_bpm)
night = Recording(study.load_subject("data/ward4.zarr", "S01"))
print(night.duration_min(), "min;", night.percent_above(100), "% above 100 bpm")
2.5 min; 42.9 % above 100 bpm

Note

self is this particular recording: the function reads its own data instead of being handed it.
